## 1. 목표와 완료 기준

T0.68의 클라우드는 `/30` 상대 주소까지만 전달했다 — 라우터 뒤 LAN은 `NO_ROUTE`.
클라우드가 각 포트에서 RIP 스피커가 되어, 붙은 라우터가 광고한 네트워크를 배우고
다른 포트로 다시 광고하게 한다 — 라우터에 정적 경로 없이 LAN끼리 통하게.

- [x] 포트별 RIP 참여 — `RipModule`(T11.2.2)을 `RipHost` 어댑터로 재사용
- [x] 학습 테이블로 데이터 평면 라우팅 (longest-prefix, 다음 홉 = 광고한 라우터의 링크 주소)
- [x] 배운 경로를 다른 포트로 재광고 (split horizon은 모듈이 처리)
- [x] `exchangeRoutes`에 클라우드 참여 + 경로 변화 diff에 클라우드 포함
- [x] 인스펙터 라우팅 테이블 (C 직결 /30 + R 배운 경로 `[120/metric]`)
- [x] 사용설명서 Cloud 절을 RIP 설정 예제로 갱신

## 2. 진행 방식

- `CloudModel`에 `RipModule`을 합성. `RipHost.rip()`은 고정 `{networks: ["1.0.0.0"]}` —
  클래스풀 A라 네 포트가 모두 참여, `interfaces()`는 링크가 있는 포트만 (끊긴 링크의
  망은 광고하지 않는다)
- `onFrame`: 목적지 MAC 검사에 `RIP_MULTICAST_MAC`을 더하고, `snapshot.rip`이 있으면
  IP 수신 전에 `RipModule.onFrame`으로 보낸다
- 전달 조회 `#lookup`: /30 상대 주소 직결 → 없으면 `#rip.routes()`의 longest-prefix
- `startRipExchange(ctx)`를 `runtime.exchangeRoutes`의 start에서 라우터들과 함께 부른다.
  교환은 RIP Router가 있어야 돈다(기존 `needsRouteExchange` 규칙 그대로)
- `currentRipRoutes`/`diffRipRoutes`에 `cloud`를 넣어 클라우드가 배운 경로도
  "경로 변화" 패널에 보이게 했다
- CloudView에 `routes: RouteEntryView[]` 추가, `fillViews`가 `model.view()`를 그대로 쓰게 바꿈

## 3. 검증

- `cloud-model.test.ts` 9개 통과 — 추가한 2개:
  - RIP를 켠 라우터 둘이 서로의 LAN을 클라우드 경유로 ping — 정적 경로 없이
    (router ping 4/4 + PC→PC 종단간)
  - RIP 없이는 /30 링크 주소까지만 닿고 배운 경로가 없다
- 디버그로 확인한 것: 링크가 없는 LAN 인터페이스는 `connectedRoutes`가
  `status === "up"`을 요구해서 광고되지 않는다 — 실제 장비처럼 `no-link`면 경로가 없다
