## 1. 목표와 완료 기준

- [x] IOS 라우터에서 `interface loopback0`(`int lo0` 등 줄임 포함)로 루프백을 만들고 `ip address`를 단다. 만들면 실제처럼 바로 켜진다
- [x] 루프백 주소로 외부 장비가 ping·traceroute·SSH를 할 수 있다 (라우터의 늘 켜진 관리 주소)

- [x] `show ip interface brief`·`show running-config`·`show ip route`(connected)에 나온다

- [x] 공통 완료 조건 (lint, 타입 검사, 단위 테스트, 빌드, 리뷰)

## 2. 진행 방식

GRE 터널과 같은 "논리 인터페이스" 구조를 따랐다 — 물리 `PORT_NAMES`에는 넣지 않고 `config.loopbacks`에 둔다.

1. shared — `LOOPBACK_NAMES`(0~3)·`isLoopbackName`, `RouterConfig.loopbacks`, `routerInterfaces()`에 병합 → 정적 경로 자기주소·중복 검사·SSH 대상·로컬 전달이 전부 자동으로 따라온다. `loopback/set`·`loopback/remove` 명령
2. 엔진 reducer — `updateLoopback` + `interface/set-ip`·`clear-ip`·`set-admin`의 루프백 분기 (터널과 같은 패턴)
3. CLI — `interface` 명령이 없는 루프백을 자동 생성(adminUp: true). `no interface LoopbackN`은 라우터 전용 파일로 — 공용 목록에 두면 스위치 파서가 매개변수를 해석하지 못해 abbreviation 테스트가 깨졌다
4. 런타임 — 루프백 연결망을 라우팅 테이블에 connected로 추가. 나가는 링크가 없어 그 서브넷의 다른 주소로 가는 패킷은 자리에서 버린다

### 주요 결정

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| 루프백 마스크는 /31·/32 허용 | `/32`가 루프백의 표준인데 `checkInterfaceAddress`는 /30까지만 받는다. `checkLoopbacks`는 완화된 검사를 쓴다 | 물리 인터페이스까지 /32 허용 (의미가 없어 보류) |
| `#unicast`에서 /31·/32 서브넷은 네트워크·브로드캐스트 검사 생략 | `checkInterfaceAddress`가 /32에 INVALID_MASK를 돌려줘 루프백 주소가 브로드캐스트로 오인돼 NOT_FOR_ME로 버려졌다 | 오류 코드를 세분화 (침투적) |
| `no interface` 터널 매개변수를 터널 이름만 받게 좁힘 | `word` 매개변수가 `loopback0`도 먹어 루프백 삭제가 터널 명령에 빨려 들어갔다 | 두 명령을 하나로 (매개변수 종류가 달라 분리가 깔끔) |
| 루프백 서브넷의 다른 주소 패킷은 조용히 버림 | 실제로도 루프백으로 배달된 뒤 버려진다 | ICMP unreachable 회신 (실제와 다름) |

## 7. 남은 일과 다음 Task에 전할 것

- 루프백은 Loopback0~3으로 제한 — 실제 IOS는 번호 제한이 없다
- 루프백을 `ip nat inside` 대상으로는 못 쓴다 (물리 인터페이스만). OSPF·router-id 개념도 아직 없다
- `routerInterfaces()`에 논리 인터페이스가 섞이니, 물리 포트만 필요한 곳은 `config.interfaces`를 봐야 한다 — 헷갈리는 곳이 `router-interface-ip.ts`의 타 장비 중복 검사(물리만 봄)
