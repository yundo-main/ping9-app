## 1. 목표와 완료 기준

Packet Tracer의 인터넷 구름처럼, 배치만 하면 붙은 장비 사이를 라우팅해 주는 가상 ISP 망.
사용자가 고른 동작 방식: **포트별 /30 링크 라우팅**.

- [x] `DeviceKind "cloud"` — 포트 Port0–Port3, 이름 접두 CLOUD, 설정 없음
- [x] 포트 순번 i에 `1.0.0.{4i}/30` 링크망 고정 배정 — 클라우드 `.{4i+1}`, 상대 `.{4i+2}` (`cloudPortInfo`)
- [x] 포트별 ARP 응답 + TTL을 줄인 전달(링크망 직결, 다음 홉 = 목적지 자신) + 자기 주소 ICMP 응답
- [x] 라우터와 같은 이유 코드(`IPV4_FORWARDED`·`TTL_EXPIRED`·`NO_ROUTE`)로 추적에 남는다
- [x] 팔레트 Cloud 버튼 + 구름 아이콘(WAN 배지) + 인스펙터 포트별 링크망 표시 + 설명서 절

## 2. 진행 방식

### shared (`document.ts`, `view.ts`, `validate.ts`, `schema.ts`)

- `DEVICE_KINDS`에 `"cloud"` 추가, `PORT_NAMES.cloud = ["Port0".."Port3"]`
- `CloudDevice`(빈 config)·`CloudView`({ports, arpTable})·`isCloudDevice`·`cloudPortInfo(index)`
- 검증: `checkDeviceConfig`는 허브처럼 null — 링크 규칙은 포트 이름 기반이라 자동으로 허용

### 엔진 (`devices/cloud/cloud-model.ts`)

RouterModel의 전달 흐름을 최소판으로 줄인 모델. 설정이 없어 정적 경로·NAT·터널·RIP가 없다.

- 포트마다 `ArpModule` — 각 포트의 클라우드 IP·MAC으로 응답, `/30` 밖의 요청엔 묵묵
- 수신 IP: 어느 포트의 클라우드 주소든 로컬 도착 → echo 응답(TTL 64)·ICMP 오류 수신·닫힌 포트 거절
- 전달: 목적지가 어느 포트의 `peerIp`인지로 나갈 포트를 고른다. TTL 1이면 `TTL_EXPIRED` + time-exceeded,
  어느 포트 상대도 아니면 `NO_ROUTE` + destination-unreachable, 들어온 포트로 되돌아가는 것도 거절
- `onConfigChanged`는 배운 ARP를 전부 비운다 (링크가 바뀌었을 수 있어서)
- 런타임: `clouds` 맵·`cloudModel()`·`runModels`·`startRun`·`configChanged`·`fillViews`·reset에 연결
- `isAdminUp`은 허브처럼 항상 true (켜고 끄는 개념이 없다)

### 화면 (`apps/web`)

- `device-icons.tsx` `Cloud` — 구름 실루엣 안에 라우터 메시(노드 5·링크 4), 우하단 "WAN" 배지
- 팔레트에 Router 묶음 뒤 `Cloud` 버튼 + 툴팁
- 인스펙터 인터페이스 행: `1.0.0.0/30 · PC1` 식으로 링크망과 상대를 표시
- `KIND_LABEL`/`KIND_NAME`/`KIND_NAMES`(오류 문구)에 `cloud: "Cloud"` — 콘솔은 허브처럼 `CLOUD1>` 프롬프트에 어떤 명령도 `unknown command`
- 도움말의 장비 목록에 클라우드 추가, `docs/manual.html`에 Cloud 절(주소 배정 규칙·정적 경로 예제)

## 4. 계획과 달라진 점

- "이미 만들어진 구름 아이콘"은 없었다 — 구름 + 메시 SVG를 새로 그렸다
- 포트는 사용자 요청의 /30 네 개 분량에 맞춰 Port0–Port3 네 개 (허브의 여덟 개보다 적다)
