## 2. 진행 방식

1. Supabase 프로젝트 `etquisloivqtbjjdbduk` (리전 Seoul) — 사용자가 대시보드에서 생성, 프로젝트 ID 전달
2. Management API로 API 키 조회 → anon key 확보 (계정 토큰은 orgs_read 권한이 없어 프로젝트 생성은 못 하고, 프로젝트 리소스 읽기는 가능했다)
3. Auth 설정: `mailer_autoconfirm=true` — 확인 메일 없이 가입 즉시 로그인. `password_min_length`는 플랫폼 하한 6이라 4로 못 낮춤 → 계정 비밀번호는 `123456`
4. Admin API로 `networked@naver.com` 생성 (`email_confirm:true`, role=student) → anon key로 password grant 로그인 검증 `LOGIN OK`
5. env 연결 — `edu/app/.env.local`(로컬) + `vercel env add`(Production) → `vercel pull` → `build --prod` → `deploy --prebuilt --prod`
6. 배포 번들에 Supabase URL이 박혔는지 grep으로 확인

### 주요 결정

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| Management API로 키 조회 | 사용자가 anon key를 직접 복사할 필요가 없다 | 키 수동 전달 |
| `mailer_autoconfirm` | 수업용 도구에 메일 확인 단계는 진입 장벽 — 학생 이메일이 확인 메일을 못 받는 경우도 있다 | 확인 메일 유지 — 가입 후 로그인까지 한 단계 더 |
| anon key만 클라이언트 env | VITE_ 접두 변수는 번들에 박힌다 — service_role 키는 절대 env에 넣지 않음 (계정 생성 1회에만 서버 측에서 사용) | service_role을 env에 — RLS를 우회하는 키가 클라이언트에 노출됨 |
