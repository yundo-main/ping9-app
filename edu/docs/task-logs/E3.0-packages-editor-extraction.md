## 1. 목표와 완료 기준

- [x] `apps/web`의 편집기 화면 전부를 `packages/editor`(`@ping9/editor`)로 이동 — 본체와 Edu가 같은 화면을 쓴다
- [x] editor 패키지가 Tauri·플랫폼 API를 전혀 모른다 — `edu/app` 빌드가 Tauri 의존 없이 가능
- [x] 본체 앱(웹 + 데스크톱)의 동작이 그대로 — 파일 저장 창, 파일 메뉴, undo/redo
- [x] 공통 완료 조건 (lint, 타입 검사, 단위 테스트, 빌드)

## 2. 진행 방식

1. `apps/web/src`의 화면 코드를 통째로 `git mv` — `components/`, `replay/`, `terminal/`, `format/`, `messages/`, `styles/`, `assets/`와 `app.tsx`, `simulator.ts`, 상태 모듈, 테스트 전부
2. `app.tsx` → `EditorApp` 컴포넌트로. 플랫폼 경계 두 개를 prop으로 뺐다:
   - `download?: (fileName, text) => Promise<void>` — 없으면 브라우저 `<a download>`(editor 안 `browserDownload`), Tauri 앱은 저장 창 구현을 넘긴다
   - `onActions?: (actions: MenuActions) => void` — 데스크톱 메뉴가 부를 동작(내보내기·가져오기·새 토폴로지·정보·undo/redo)을 넘긴다
3. `topology-file.ts`에서 Tauri 의존 두 함수(`downloadText`의 저장 창 분기, `pickImportFile`)를 `apps/web/src/file-platform.ts`로 이동. editor엔 순수 함수 + `browserDownload`만 남겼다
4. `apps/web/src`가 얇아졌다: `main.tsx`(EditorApp 렌더 + prop 연결) + `file-platform.ts`(Tauri 전용 구현 + `listenTauriMenu`)
5. 공개 표면은 `index.ts` — `EditorApp`, `MenuActions`, `simulator`, `useSnapshot`. 스타일은 `@ping9/editor/editor.css` export로 import

### 주요 결정

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| `App` 이름을 `EditorApp`으로 | 패키지 공개 API라 앱과 구분 필요 | `App` 그대로 — edu/app과 이름이 겹친다 |
| 저장을 prop으로 | Tauri 플러그인 import가 edu 빌드를 깬다. prop 없으면 브라우저 다운로드로 떨어져 양쪽 다 동작 | `window.__TAURI_INTERNALS__` 분기를 패키지에 둠 — dynamic import라도 vite가 모듈 해석을 시도해 edu 빌드가 깨진다 |
| 메뉴 액션을 `onActions` 콜백으로 | 컴포넌트 안의 최신 클로저(exportTopology 등)를 ref 경유로 넘겨 메뉴가 항상 현재 동작을 부른다 | 컴포넌트가 메뉴 이벤트명을 앎 — Tauri 지식이 패키지로 새어 들어간다 |
| `apps/web`은 콘솔만 남김 | web의 역할이 "EditorApp + Tauri 껍데기"로 명확해졌다 | `src/`에 화면 일부 유지 — 다시 갈라지는 길 |
